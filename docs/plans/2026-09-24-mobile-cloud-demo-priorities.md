## P0-2a／P0-2b 操作流程與安全驗收（新增）

### A. 手機訂單查詢

1. 結帳成功顯示訂單編號、簡要明細、「查詢訂單」與保存資訊提醒；無 Email 也能完成。
2. 查詢表單輸入訂單編號＋購買時手機末三碼；只做輔助核對，不可據此無限制回傳個資。展示版可用固定假訂單驗證畫面；正式版採安全查單連結或一次性驗證碼，需有過期與撤銷策略。
3. 驗證通過後顯示商品、規格、總額、付款狀態（待付款／已付款／失敗／退款等）、配送／自取及出貨狀態、店家聯絡方式；敏感資訊遮罩。
4. 找不到／末三碼錯誤／驗證過期以一致、安全的錯誤訊息處理；設查詢限流、不可枚舉識別碼和存取紀錄，避免透露帳戶／電話是否存在。
5. 手機重新整理與跨裝置查詢應由具權限與安全控制的後端讀取訂單；不可僅靠 localStorage 當成正式查單。

### B. 購買後 Email 自動推送

1. 結帳填寫電話（必填）與 Email（選填）；若有 Email，對地址做基本格式檢查但不額外強制建立會員。
2. 訂單成功持久化後觸發「訂單成立」通知，內容包括訂單編號、品項及金額、付款方式／狀態、配送方式、聯絡入口及具期限的安全查單連結。與交易無關的行銷資訊不得混入交易通知。
3. 發信採非同步任務、冪等鍵／事件去重、有限重試、失敗紀錄及後台可查狀態；建立訂單與發信錯誤分開處理。不得因發信失敗重建訂單或重複扣款。
4. 後續可按實際事件推送「確認收款／出貨／取消或退款」Email；實際訊息只依後端已確認狀態發送，不可把模擬付款當成正式收款。
5. 測試有 Email、無 Email、Email 格式錯誤、發信失敗／重試／重複事件、通知連結過期，以及收件者是否可用手機開啟查單頁。
6. Demo 採 sandbox 郵件服務或假發信並明示「測試通知」；正式啟用前確認發信網域 SPF／DKIM／DMARC、郵件供應商設定、個資與通知範本。不得在 GitHub 留 SMTP 密碼／API 金鑰。

**設計決策：** 手機「末三碼」是游老師指定的使用體驗；但安全驗證方式仍應由受控後端處理。既有「Email 可選填、手機必填」決策維持不變。

### C. 手機驗證與簡訊／推播流程

1. 顧客在結帳時填手機號碼（必填），使用台灣手機號碼格式檢查與標準化；號碼「有填」不代表「本人已驗證」。首次建立測試訂單時可先用假手機號碼，不發真實訊息。
2. 需要驗證時送出一次性簡訊 OTP：輸入號碼→告知驗證用途→發送代碼→輸入代碼→後端核對→標記已驗證的手機／訂單範圍。OTP 過期、重送、錯誤次數、變更號碼及無法收簡訊都要有復原路徑與店家人工協助。
3. 會員免註冊結帳維持可行；購買後以「訂單編號＋末三碼」啟動查詢，再用綁定手機的 OTP 或有效且高熵的查單連結驗證身分。不可僅用末三碼顯示完整訂單、地址或聯絡資料。
4. 訂單成功、確認收款、出貨可發送交易簡訊（須有適用通知設定及成本控管）；內容僅含必要資訊，不附完整個資。通知事件用冪等鍵避免重複，發送失敗留紀錄並提供 Email／人工聯繫等備援，不能因通知失敗撤銷訂單。
5. 如果啟用 Web Push，須顧客明確同意，且可隨時關閉。先檢測手機是否支援與授權；iPhone 在相關條件未滿足時提供簡訊／Email 替代。訂閱與裝置權杖由後端保護，不將訂單資訊直接曝光於鎖定畫面。
6. Demo 測試：驗證成功、錯誤與過期、重送限流、手機更換／號碼更動、拒絕推播、無 Email、簡訊供應商失敗及不同裝置查單；不對顧客真實號碼亂發測試訊息。真實簡訊費用、供應商、正式推播通道另確認。

**注意：** 簡訊 OTP 是確認持有該手機號碼，不等於確認法律身分或付款人本人。需要處理訂單修改／取消、地址變更或退款等高風險操作時應再次驗證。

### D. 結帳步驟門檻：先手機、後地址、再付款（2026-09-24 最新決策）

1. 購物車按「前往結帳」→ 輸入手機號碼 → 發送並驗證一次性簡訊 OTP；驗證通過才解鎖下一步。驗證失敗／過期／重送上限時保留購物車，不進入地址或付款。Demo 使用模擬 OTP，禁止向真實顧客亂發訊息。
2. 已驗證手機後選「宅配／到店自取」。宅配才顯示收件資料：姓名、縣市／鄉鎮區、郵遞區號、路街門牌、樓層、必要備註。先檢查欄位與郵遞區號區域對應，再使用可用地址服務進一步查核及標準化；地址服務未接妥時不得宣稱已驗證地址。顧客需看見並確認建議的正規化地址。
3. 地址驗證結果分三態：`VERIFIED`（可配送、進下一步）、`NEEDS_CUSTOMER_CORRECTION`（缺欄位／可修正，顯示具體原因和候選）、`ADDRESS_REVIEW_REQUIRED`（地址不存在、歧義、偏遠限制、服務不可用或顧客無法修正；留存待覆核事件）。到店自取使用 `PICKUP`，無宅配地址檢查。
4. `VERIFIED` 或 `PICKUP` 才開放運費確認、付款方式與最終確認；**付款授權／收款只能發生在身分與配送必要資訊確認後**。最終送出由後端重查驗證狀態，不能只靠前端解鎖。
5. `ADDRESS_REVIEW_REQUIRED`：先提供「修改地址」或「請店家協助」；顯示尚未完成正式下單／付款，若營運需要可建立不扣款、不可出貨的待聯繫草稿。店家後台收到通知，致電確認、記錄修正及覆核人員／時間，重新驗證或人工核准後才放行付款／出貨。地址人工核准不等於配送商保證可送達；出貨前仍須確認可配送。
6. 對於已付款後才發現配送異常的例外訂單，立即暫停出貨、通知店家與顧客，按已確認的換址、取消或退款流程處理，不能自動重複扣款。
7. 驗收至少覆蓋：手機 OTP 成功／錯誤／過期；地址正確／缺門牌／郵遞區號不符／查無地址／服務中斷；自取不要求宅配地址；人工覆核後恢復流程；未核准不能付款與出貨；刷新頁面不得繞過後端門檻。Demo 使用明示的假資料及模擬付款。

**未定營運決策：** 如地址無法驗證，預設不開放付款並轉人工協助。若陳老師希望先保留訂單或採匯款後人工覆核，須另確認狀態、付款時點與退款責任，不得自行變更。

### E. 顧客與會員：一次交易循環完成才納入名單（2026-09-24 最新決策）

**狀態模型（先規劃，未驗證實作）：**

- `PHONE_VERIFIED_VISITOR`：OTP 確認手機號碼持有權，不等於核實自然人，也不自動建立正式會員。
- `ORDER_CUSTOMER_PENDING`：已建立訂單；可保留依法及履約必要的交易／聯絡資料，但不將其標為完成交易的會員。
- `PAID_PENDING_FULFILLMENT`：實際款項已確認，待宅配交付或門市自取核銷；只標為交易進行中。
- `COMPLETED_CUSTOMER`：付款與實際交付／自取皆有後端佐證，且沒有未解的配送／身分例外；記錄完成交易的顧客關聯。單一完成交易只能作為履約可信度訊號，不能認定唯一自然人。
- `MEMBER_ACTIVE`：顧客符合會員資格、明確選擇加入（如有會員方案）且依已確認會員規則建立；交易完成不自動等於同意入會或接收行銷。

**流程與驗收：**

1. 每次結帳仍可免註冊；保留訂單與依法必要交易資料，和會員／行銷名單分開儲存。用不可猜測顧客 ID 建關聯，手機號碼只作聯絡及驗證因素；一個號碼可能由多人使用。
2. 只有後端核實的付款成功、宅配交付證據或自取核銷，且無未決爭議，才觸發「交易完成」事件；事件冪等且可追溯來源、時間與責任人。單純建立訂單、發信成功、OTP 成功、模擬付款或印出宅配單都不算循環完成。
3. 如果門市由陳老師人工確認交付，須有管理者權限、紀錄核銷人與時間，不能由訪客自行改成完成。退款、拒收、未取件、代購／不同收件人及聯絡資訊衝突，進待覆核；不得自動合併會員。
4. 會員名單收錄規則與交易完成記錄分離：先確認陳老師要的是「已成交顧客名單」還是「自願加入會員名單」。若尚未確認，預設不自動入會，不寄行銷訊息；交易狀態通知依履約必要與適用設定發送。
5. Demo 使用假顧客與模擬交付事件測試：OTP 但沒買、買了未付款、已付款未交付、已交付、退款、同手機不同姓名／多人、手動交付、重複事件，以及顧客不同意入會。測試資料不得混進正式名單。
6. 若未來要驗證法律身分或防冒名，另訂必要且合乎比例的身分核驗規格，不能宣稱本流程已完成真實身分認證。

## F. 陳老師低負擔營運驗收：防棄用檢查（2026-09-24）

**成功定義：** 網站不是只要能下單，而是日常營運不增加不可控負擔；正常訂單盡量自動流轉，只有確實需要人判斷的異常才提示店家。這些屬「待實作／待店家驗收」要求，不得先標完成。

| 優先 | 風險／要核查的事 | 驗收與降級規則 |
|---|---|---|
| 上線前必須 | 單一待辦工作台 | 陳老師打開後台只看「今天要處理」：待核帳、待包裝、待出貨、待人工覆核、待客服；每張單清楚呈現下一個動作、截止／優先程度、負責人與處理歷程；一般成功事件不得反覆打擾。 |
| 上線前必須 | 防重複扣款／超賣／漏單 | 同筆下單、金流回呼、通知及出貨任務皆冪等；付款／庫存／訂單狀態具一致性及異常補償；結帳量超過可用庫存時暫停該商品銷售，不能只靠前台售完標籤。 |
| 上線前必須 | 統一通知與例外 | 付款、地址、配送、OTP／Email 失敗與退款等進同一例外隊列；同一事件合併告警、有限重試，須人工處理才提示，禁止無限重送或把所有失敗都丟給陳老師。緊急程度與通知時間待店家確認。 |
| 上線前必須 | 電話老顧客與人工補單 | 保留電話／到店下單；後台可低欄位建單、標記已驗證／待驗證、核帳／交付並依相同規則防重複；不能強迫熟客操作手機 OTP；人工例外須留操作紀錄。 |
| 上線前必須 | 極簡包裝與出貨 | 顯示品項、規格、數量、配送資訊和一鍵產出揀貨／包裝單；防貼錯標籤；宅配託運／物流狀態能核對；未驗地址或未確認付款不得放行出貨。 |

| 上線前必須 | 對帳、退款與客服 | 每日可讀的收款／待核帳／退款／未出貨清單；可追蹤匯款辨識與異常付款；顧客能自助查單，常見問題有清楚說明，異常才需要陳老師介入。 |
| 上線前必須 | 安全、備份與權限 | 管理員最小權限、登入保護、操作稽核、個資遮罩與留存／刪除政策；備份含訂單、商品、媒體、付款狀態及還原演練；測試與正式資料完全隔離。 |
| 上線前必須 | 成本與維護責任 | 列出雲端、網域、簡訊、Email、金流、物流、圖片 AI 的固定／單筆成本與預算提醒；指定故障聯絡人、更新與備份責任，避免陳老師成為系統管理員。 |
| Demo 前 | 真實操作演練 | 用手機讓陳老師不看工程文件走一筆正常模擬訂單、查單、後台處理與一筆異常；記錄每步所需時間、卡點、求助次數與意見，不能把能操作 Demo 等同可正式營運。 |

### 失敗演練與放行門檻

- 模擬：簡訊收不到、Email 寄不出、同時最後一包被兩人買、付款成功但網頁超時、重複付款回呼、地址不明、物流拒收／退件、電話單與網路單重複、網路斷線、管理員誤操作及備份還原。每項須證明「資料不遺失、錢不重扣、不能錯誤出貨、恢復後可追查」。
- Demo 放行：完整手機購買／查單／通知／地址例外與後台待辦能用**假資料**演示；不能因外部供應商未接妥而假稱正式可營運。
- 正式營運放行：由陳老師確認操作與人力負荷、商家服務／成本與通知責任、備份還原／故障演練、正式付款及配送整合。若缺任何重大保障，維持測試版，不開放真實收款。
- 不替店家擅設可接受的每日訂單量、處理分鐘數、簡訊預算或客服時段；先實測後與陳老師共同訂定可量測門檻。
