## P0-2a／P0-2b 操作流程與安全驗收（新增）

### A. 手機訂單查詢

1. 結帳成功顯示訂單編號、簡要明細、「查詢訂單」與保存資訊提醒；無 Email 也能完成。
2. 查詢表單輸入訂單編號＋購買時手機末三碼；只做輔助核對，不可據此無限制回傳個資。展示版可用固定假訂單驗證畫面；正式版採安全查單連結或一次性驗證碼，需有過期與撤銷策略。
3. 驗證通過後顯示商品、規格、總額、付款狀態（待付款／已付款／失敗／退款等）、配送／自取及出貨狀態、店家聯絡方式；敏感資訊遮罩。
4. 找不到／末三碼錯誤／驗證過期以一致、安全的錯誤訊息處理；設查詢限流、不可枚舉識別碼和存取紀錄，避免透露帳戶／電話是否存在。
5. 手機重新整理與跨裝置查詢應由具權限與安全控制的後端讀取訂單；不可僅靠 localStorage 當成正式查單。

### B. 購買後 Email 自動推送

1. 結帳填寫電話（必填）與 Email（選填）；若有 Email，對地址做基本格式檢查但不額外強制建立會員。
2. 訂單成功持久化後觸發「訂單成立」通知，內容包括訂單編號、品項及金額、付款方式／狀態、配送方式、聯絡入口及具期限的安全查單連結。與交易無關的行銷資訊不得混入交易通知。
3. 發信採非同步任務、冪等鍵／事件去重、有限重試、失敗紀錄及後台可查狀態；建立訂單與發信錯誤分開處理。不得因發信失敗重建訂單或重複扣款。
4. 後續可按實際事件推送「確認收款／出貨／取消或退款」Email；實際訊息只依後端已確認狀態發送，不可把模擬付款當成正式收款。
5. 測試有 Email、無 Email、Email 格式錯誤、發信失敗／重試／重複事件、通知連結過期，以及收件者是否可用手機開啟查單頁。
6. Demo 採 sandbox 郵件服務或假發信並明示「測試通知」；正式啟用前確認發信網域 SPF／DKIM／DMARC、郵件供應商設定、個資與通知範本。不得在 GitHub 留 SMTP 密碼／API 金鑰。

**設計決策：** 手機「末三碼」是游老師指定的使用體驗；但安全驗證方式仍應由受控後端處理。既有「Email 可選填、手機必填」決策維持不變。
