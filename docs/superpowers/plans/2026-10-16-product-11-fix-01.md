# PRODUCT-11-FIX-01 商品儲存確認與持久化驗證 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make draft creation report success only after the server returns a persisted product ID and the same authenticated session re-reads that ID from the catalog.

**Architecture:** Keep the existing file-backed Demo catalog and atomic replacement boundary. Extend the publishing service result to carry the server-created product, add a same-session read-after-write verification at the new-product page, and expose bounded request/instance/write/sync diagnostics without secrets or personal data. Add isolated filesystem and component tests for persistence, verification failures, duplicate prevention, publication isolation, and regression behavior.

**Tech Stack:** Next.js App Router, TypeScript, React, Vitest, Testing Library, pnpm.

**Spec:** Approved in chat as PRODUCT-11-FIX-01 on 2026-10-16; formal defect requirements are in the user request.

## Global Constraints

- Do not modify Acer production containers, catalog.json, formal photos, DNS, Tailscale, deployment settings, or CLOUD work.
- Use synthetic products and isolated temporary data directories for tests; never copy formal data into uncontrolled environments.
- A successful save must include a persisted product ID and same-session GET verification.
- GET failure must not be reported as POST failure and must instruct the operator not to resubmit.
- Do not create a second product automatically after an uncertain read-back.
- Preserve existing product edit, photo, draft, publication, and public-catalog behavior.
- Commit and push only this independent branch; do not merge or deploy.

## Review Focus

- Atomic file replacement and cross-instance concurrent writes must not silently discard products; covered by store concurrency/persistence tests.
- Public synchronization failure after catalog persistence must be surfaced as a distinct pending-sync result; covered by route/service tests.
- A successful POST followed by a failed verification GET must preserve the user's draft and avoid a second POST; covered by component tests.
- A malformed or missing server product ID must never enter the success state; covered by service/component contract tests.
- Existing photo replacement, edit, draft visibility, and publication toggles must remain green in the full suite.
