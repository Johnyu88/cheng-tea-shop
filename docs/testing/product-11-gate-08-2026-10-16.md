## Formal deployment admission checklist — design only

1. Obtain explicit approval for option A or B, the deployment window, and a write-freeze period. No formal backup or freeze was performed here.
2. Before the window, read-only verify the formal container name, image digest, ports, bridge network, command, user, environment names, and mount paths. Confirm the original image is present by digest; do not substitute a Git SHA or `reauth-05f058e`.
3. Ask the operator to stop admin writes at the ingress for the short window, with a visible maintenance message or controlled 503. Do not rely on users merely refraining from clicks. Confirm no in-flight POST/PATCH before backup.
4. Create an approved protected backup of `catalog.json`, `publication.json`, `catalog-media`, public `media`, `packing-photos`, and order/auth/identity/outbox SQLite files as required by the data owner. Record UTC timestamp, byte sizes, SHA-256 hashes, and a separate restore-read test. This step is not executed.
5. Capture a pre-switch inventory from the approved authenticated session: total count, every product ID, draft/published state, photo references, and order count. Keep product contents out of logs.
6. Verify the candidate image digest and its build/source evidence. If source provenance remains unknown, stop unless the release owner accepts that risk explicitly.
7. Switch only the approved application image, preserving mounts, ports, network, command, environment names, Caddy, Tailscale, and DNS. Do not mix the old and candidate writers against the same data without the write freeze.
8. Verify health and login, then use one authenticated session to GET the admin list. Compare count, all pre-switch IDs, draft/published states, and photo references. Confirm the public list contains only published items and media resolves.
9. Do not retry any failed POST solely because a subsequent GET is unavailable. A POST with unknown persistence must be treated as uncertain and investigated by ID/logs.
10. End the freeze only after the post-check is recorded and the operator approves reopening writes.

## Rollback conditions and procedure — design only

Stop and roll back if the candidate image cannot start, the approved mount paths differ, any pre-existing ID is missing, a photo is inaccessible, draft content is public, public sync is inconsistent, or diagnostics show an unconfirmed write.

1. Re-enter the write freeze and preserve candidate logs, image digest, request IDs, and sync status.
2. Confirm the original formal image exists locally by the exact digest and that the deployment host can use it. Local image startup is not registry pullability proof.
3. Restore the original container definition, image, command, ports, network, environment names, and mounts. Do not use Git source SHA as a container rollback.
4. Start the original image without restoring data automatically. Verify health, admin list, all IDs, photos, drafts, publication state, and public media.
5. Restore catalog/public/order data only after explicit data-rollback approval and backup hash verification. Preserve the failed candidate data separately for investigation.
6. Reopen writes only after rollback verification is signed off.
