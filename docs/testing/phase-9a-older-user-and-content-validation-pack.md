狀態：**準備完成，尚未執行真人走查**。本文件不是研究結果，也不以 dry run 或 e2e 推論真人理解。

- 只在受控本機環境執行；目前不啟動 preview、正式部署、付費服務、Docker、登入、資料庫、真實付款、物流或 ERP。
- 真人 session 不得輸入真實姓名、電話、地址、付款資料、帳號或可識別照片。使用測試值：姓名「陳小姐」、手機「0912000000」、地址「茶行路 1 號」。
- 不錄音、不錄影、不保存螢幕截圖中的個資，除非另有明確同意與受控保存位置；本 repo 只提交去識別化摘要。
- 主持人不得暗示答案、指出按鈕位置或替參與者操作；只能提供中性提示並記錄提示次數。

## 2. 執行前 preflight

主持人執行：


- 本機 URL 可開啟，且使用目前已驗證的 standalone build 或明確核准的 localhost dev server。
- viewport 至少包含 `360×800` 與 `1280×800`。
- T1–T8 腳本、觀察模板與素材替換清單已備妥。
- 參與者同意開始、可隨時停止，且主持人知道停止與清除測試輸入方式。
- 所有畫面仍明確標示 placeholder、合成 checkout、synthetic publish，不把 prototype 當作正式交易。

## 3. 主持人最終腳本

### 開場與同意

「今天不是考試，也不是測試您；我們是在看網站是否容易理解。請照您平常的方式操作，想到什麼可以說出來。如果任何地方不清楚，請直接告訴我。我不會因為您按錯而責怪您，您可以休息或隨時停止。」

開始前再次確認：不輸入真實個人資料、不輸入付款資料、不上傳真實照片；本次 checkout 與上架都是合成原型。

### 主持規則

1. 一次只念一個任務，不先說明控制項位置。
2. 等待參與者自行找路；停頓約 30 秒才問：「您現在在找什麼？」
3. 仍無進展時只給中性提示：「請繼續找下一步，不用擔心按錯。」並記錄提示。
4. 不把「完成很快」當成理解良好；要求參與者用自己的話說明結果。
5. 每個任務結束問：「剛才哪裡最清楚？哪裡最不清楚？」

### T1–T8 任務

| 任務 | 念給參與者的話 | 任務完成條件 | 必記觀察 |
|---|---|---|---|
| T1 商品理解 | 「請在首頁找一款您想了解的茶，說說您怎麼知道它是什麼茶。」 | 找到商品詳情，能說出茶名、口感或規格至少一項 | 字體、商品卡、照片 placeholder、商品資訊理解 |
| T2 加入購物車 | 「請查看這款茶是否有貨，選擇 2 份加入購物車。」 | 正確品項、數量 2、小計正確 | 按鈕大小、數量控制、供貨狀態、價格理解 |
| T3 進入 checkout | 「請從購物車前往結帳，填入合成資料，走到確認訂單。」 | 完成聯絡與配送資料並到確認畫面 | 導覽、欄位標籤、步驟順序、資料保留 |
| T4 錯誤修正 | 「請故意不填手機就按下一步，再修正。」 | 看到錯誤、補手機後繼續，姓名仍保留 | 錯誤位置、文字理解、修正路徑 |
| T5 返回購物車 | 「請回到購物車，確認剛才的茶與數量還在。」 | 確認品項、數量與小計 | 返回方式、是否迷路、狀態保留 |
| T6 建立草稿 | 「請到商品上架原型，建立叫春茶的 150g 商品，價格 1200，選烏龍茶、標記有貨，先存草稿。」 | 最低欄位完成且看到草稿成功 | 字體、欄位、選單、原型提示理解 |
| T7 檢查文案 | 「請產生介紹草稿，看看是否只使用您填的資料，再切換電腦版與手機版預覽。」 | 文案可編輯、預覽可切換，未捏造產地或功效 | 商品理解、文案可信度、placeholder 辨識 |
| T8 合成發布 | 「如果內容確認無誤，請勾選確認並上架。」 | 先勾選確認，再看到合成上架成功 | 確認門檻、成功訊息、是否誤以為正式上架 |

T1–T5 是顧客主要路徑；T6–T8 是店家／操作員情境。若 session 時間不足，保留 T2、T3、T4、T6，並記錄未執行任務，不得推估結果。

## 4. 觀察紀錄表

使用 `phase-9a-observation-template.md`。每個 session 只使用去識別化 Session ID，不記姓名或聯絡方式。

每項任務記錄：完成／部分完成／失敗、耗時區間、提示次數、誤觸、停頓、參與者原話（去除個資）、主持人介入、是否誤解 prototype 邊界。

觀察類別：

- 字體與閱讀
- 按鈕大小與可點擊性
- 導覽與返回
- 商品名稱／口感／規格／價格／供貨理解
- 加入購物車與小計
- checkout 三步與 prototype payment boundary
- 錯誤提示與修正
- placeholder、synthetic data、合成發布理解

## 5. 問題分級 P0–P3

| 分級 | 定義 | 處理規則 |
|---|---|---|
| P0 | 主要任務無法完成、資料遺失、誤導成真實付款／正式上架，或有安全／隱私風險 | 立即停止該路徑，未修正前不得進行下一場同路徑測試 |
| P1 | 需要主持人代操作或明確指出控制，或多數參與者無法恢復 | 下一場真人走查前修正，或由產品決策明確接受風險 |
| P2 | 可完成但明顯困惑、反覆尋找、錯誤提示難理解或 prototype 邊界不清 | 彙整後排入下一個核准切片；不得以自動化通過抵銷 |
| P3 | 不阻斷任務的文案、間距、視覺或小幅效率改善 | 排入 backlog，不影響本輪通過 |

若同一問題跨兩位參與者重現，至少升為 P1 重新評估；不因單次主觀偏好直接改 UI。

## 6. 真實商品照片與文案替換清單

詳見 `phase-9a-real-content-replacement-checklist.md`。任何真實內容替換前，必須有來源、授權、事實證據與 owner；未確認者保持 labeled placeholder 或 synthetic copy。

## 7. 驗證完成條件

Phase 9-A 真人走查準備不等於完成研究。只有在下列條件都滿足後，才可標記「真人走查完成」：

- 至少一場已取得同意的真人 session，並保留去識別化觀察紀錄。
- T1–T5 每項有完成／部分／失敗判定；未執行項目明確標記。
- 沒有未處理的 P0；每個 P1 有修正 commit、明確接受決策或暫停理由。
- P2/P3 有 owner、優先級與下一步，不把主觀偏好寫成產品事實。
- 參與者是否理解 placeholder、synthetic checkout、無真實付款、無正式上架，均有直接口語證據或明確誤解紀錄。
- 真實照片／文案替換清單逐項標記 evidence、授權與狀態；沒有以合成資料冒充真實內容。
- `WHITEPAPER.md` 記錄研究範圍與限制；`HANDOFF.md` 記錄可重現問題與下一步；`CAPABILITY_MAP.md` 更新 human-validation／real-content status。

## 8. 真人測試後文件回填方式

只回填彙整結果，不提交個資、錄音、原始截圖或未授權商品素材：

1. 在 `docs/testing/` 保存去識別化 session summary 與 issue IDs。
2. `WHITEPAPER.md`：新增日期、參與人數區間、執行任務、客觀觀察、限制與 P0–P3 摘要；明確區分觀察與推論。
3. `HANDOFF.md`：記錄分支／commit、測試環境、未完成任務、待修問題、是否需要真人複測；更新下一步，不宣稱未測項目通過。
4. `CAPABILITY_MAP.md`：只把有直接真人證據的能力從「must validate」移動；real content 只有在來源／授權／事實證據齊全時更新。
5. 若要修正 UI，另開小切片，先附 issue ID 與重現步驟，再測試、commit、push；不要在研究紀錄中直接改 code。
